| tifffile | 2026.9.9 | |
| onnxruntime | 1.30.0 | 可用于深度学习去卷积 |
| matplotlib / pandas | 已打包 | |
| **scipy** | **未打包** | |
| **skimage / sklearn** | **未打包** | |

**这一条直接决定技术路线**：原计划里依赖 scipy 的算法（配准、连通域、去卷积），现在全部改用 **cv2 或纯 numpy** 实现，不新增依赖。详见附录 A。

### 2.2 处理链原则（本次改造的架构基础）

P1-7（配准/背景扣除）和 P1-8（去卷积）都会改变像素值。如果直接改 `item._cache`，后果是：不可逆、不能对比、不能只对导出生效、工程文件存不下。

**统一约定：原始像素永不被修改。** 所有处理以"处理链"形式记录，预览和导出时按链重建。

```python
# core/model.py 新增
@dataclass
class ProcessStep:
    kind: str                                   # "register" | "bg" | "deconvolve"
    params: dict = field(default_factory=dict)
    enabled: bool = True

# ImageItem 新增字段
process: list = field(default_factory=list)     # list[ProcessStep]
```

- 处理链进 `.icproj`（P0-1 已包含）。
- 每个步骤可单独 `enabled = False`，界面上一键对比开/关效果。
- **推荐顺序**：通道配准 → 背景扣除 → 去卷积。界面上按这个顺序排列，不允许用户打乱（打乱会出现难以解释的结果）。
- 任何处理都会让缓存失效 → 见 2.3。

### 2.3 缓存失效规则（必改）

现状：`ImageItem._cache` 是一个裸属性，`load_stack()` 判 `is not None` 就返回。加了处理链之后，改一下配准参数，缓存不会失效，界面显示旧数据。

**约定**：缓存 key 必须包含处理链指纹。

```python
def process_fingerprint(item):
    return json.dumps([asdict(s) for s in item.process], sort_keys=True)

# load_stack() 内部
key = (process_fingerprint(item), item.path)
if getattr(item, "_cache_key", None) == key:
    return item._cache
```

`_preview` 同样处理（它现在的 key 是 `("planes", frame, max_side)`，缺处理链）。

### 2.4 线程模型

- **所有耗时操作必须走 `FnWorker`**。判据：单张图超过 200 ms 的处理一律进后台线程。
- 新增的耗时项：`job_export` 里的原始位深导出、去卷积、拼接、批量背景扣除、批量配准。
- worker 必须支持进度上报（沿用 `report(i, total, msg)`）和取消（新增 `self._stop` 检查点，参考 `ThumbWorker` 的写法）。
- **UI 线程里不允许出现 `cv2.x` 的重算子调用、`np.fft.*`、`np.percentile` 全图计算。**

### 2.5 兼容性

- `config/settings.json` **继续保留**，作为"全局默认值"；`.icproj` 内嵌一份 `settings` 快照，打开工程时覆盖。
- 老 `settings.json` 必须能被新版本读（`Settings.load()` 已经是"缺字段用默认值"的宽容策略，保持）。
- `Settings.migrate()` 沿用现有的版本号迁移机制，本次新增 `settings_version = 3`。
- `.icproj` 自带 `schema` 字段，未来版本迁移同理。

### 2.6 界面文案规范

- 全部中文，术语沿用现有文案（"裁剪视野""新标尺""标定""组内裁剪框位置一致"）。
- 新按钮不加 emoji。
- 参数留空 = 自动，沿用现有约定，输入框里显示灰色占位而非 0。

### 2.7 显示清晰度冻结（硬约束，N1）

**用户明确表态：现在导入后的清晰度是满意的，本次改造不得让观感发生变化。**

冻结的是这条链路（改造期间**只允许重构、不允许改算法与参数**）：

| 位置 | 被冻结的内容 |
|---|---|
| `render.preview_for_view()` | 一次性 LANCZOS 重采样；`shrink >= 3` 时的 numpy 箱式预缩；目标尺寸 = 画布尺寸 × dpr |
| `render.preview_planes()` | `max_side=1100` 的降采样缓存 |
| `main_window._preview_full()` | `shrink >= 1.6` 时调用的 `render.sharpen_display()`（半径 1.3 / 75% / 阈值 2） |
| `render.sharpen_display()` | 参数与"只在整图缩小显示时生效"的判据 |
| `render.compose()` | 显示区间 → 8bit 的映射方式（线性、`np.maximum` 叠加） |
| `canvas.paintEvent()` | 渲染路径、`SmoothPixmapTransform` 的使用 |

**允许变化的场合（唯一的例外）**：

- 用户**主动启用**了处理链（配准 / 背景扣除 / 去卷积）时，画面按处理链结果变化——这是功能本身；
- 用户**主动**改了显示区间、配色、导出放大等参数时。

除上述两种情况外，**默认状态下的观感必须与 v1.1 逐像素级别一致**。

**回归验收（每个改造项合并前必须跑）**：

```powershell
& "E:\ImageCapture\runtime\python\python.exe" "E:\ImageCapture\tests\sharp_and_bar_check.py"
```

1. 固定一张图（OIB 或 CZI）+ 固定画布尺寸，取"原图显示"与"裁剪结果"两张截图；
2. 与 v1.1 基线截图比较**拉普拉斯方差**，偏差必须 **< 5%**；
3. 同时人工肉眼确认一次（离屏截图 → 看图）。

基线截图在本次改造开始前先存一份到 `output\_自检\清晰度基线\`，改造后逐项对比。
**任何一个改造项让这条断言变红，先回退该改动再查原因**——不要"顺手优化"这条链路。

### 3.2 问题

关闭程序后丢失：导入的图片清单、每张图的 `umpp`（含手动画线标定）、分组、改过的组名、每组的裁剪框位置（µm）、关掉同步后每张各自的位置、手拖的标尺位置、当前选中状态。

后果不只是"要重做一遍"——**裁剪框位置是主观判断，重做一遍得到的框和昨天不是同一个，同一批数据两次出的图不一致，这是方法学硬伤。**

另外 `Group.key` 由类级计数器 `Group._seq` 生成（`model.py:166`），**每次启动都从 k1 重新开始**，所以 key 天然不能跨会话存活——工程文件必须显式处理。

### 3.3 目标

`.icproj` 工程文件承载完整工作区；支持手动保存、自动保存、崩溃恢复；支持撤销。

### 3.4 设计

#### 3.4.1 文件格式

UTF-8 JSON，扩展名 `.icproj`，默认放在用户选择的位置。完整结构：

```json
{
  "app": "ImageCapture",
  "schema": 1,
  "saved_at": "2026-09-22T10:30:00",
  "settings": { },
  "groups": [ ],
  "items": [ ],
  "view": { }
}
```

| 顶层字段 | 类型 | 说明 |
|---|---|---|
| `app` | str | 固定 `"ImageCapture"`，用于识别非法文件 |
| `schema` | int | 从 1 开始，用于迁移 |
| `saved_at` | str | ISO 8601 |
| `settings` | object | `Settings.to_dict()` 全量 |
| `groups` | array | 见 3.4.2 |
| `items` | array | 见 3.4.3 |
| `view` | object | `{"group": gid, "item": path, "t": int, "z": int, "mode": "full"\|"crop"}` |

#### 3.4.2 groups 条目字段

| 字段 | 序列化 | 说明 |
|---|---|---|
| `gid` | 是 | 组 ID |
| `key` | 是 | **稳定标识，必须存**（见 3.4.6 坑 2） |
| `title` | 是 | 显示名 |
| `title_manual` | 是 | 用户改过名字 |
| `sync` | 是 | 组内裁剪框位置一致 |
| `keep_empty` | 是 | 手工建的空组保留 |
| `out_dir` | 是 | 本组独立输出目录 |
| `box` | 是 | `{x, y, w, h}`，单位 µm |
| `boxes` | 是 | `{path: {x,y,w,h}}`，关掉同步后逐张位置 |
| `bar_anchor` | 是 | `[nx, ny]` 或 null |
| `bar_text_anchor` | 是 | `[nx, ny]` 或 null |
| `images` | **否** | 由 `items` 反查重建，不重复存 |

#### 3.4.3 items 条目字段（白名单）

`ImageItem` 是 dataclass。**用显式白名单，不用 `dataclasses.asdict()`** —— 理由不是"会崩"
（实测 `asdict()` 没问题，见 §3.4.6 坑 1 的更正），而是**字段集合必须可控**：
以后加字段、改字段都能有明确的迁移点，不会因为某个内部属性被顺手写进工程文件而变成隐性契约。

**白名单一次定全**（把 P0/P1 所有字段都列进来，未实现的部分留默认值）——
否则每上一个 P1 项都要改一次 schema、写一次迁移：

```python
ITEM_FIELDS = (
    "path", "name", "group", "umpp", "calib", "width", "height",
    "frames", "bits", "series", "note",
    "group_manual", "group_key",
    # —— P0-3 新增 ——
    "t_count", "z_count", "z_step_um", "t_interval_s", "z_declared_manual",
    # —— 2.2 处理链 ——
    "process",
    # —— P0-4 新增 ——
    "range_mode", "ref_frame",
    # —— P1-5 新增 ——
    "proj_mode", "proj_from", "proj_to",
    # —— P1-6 新增 ——
    "rois",
    # —— P1-9 新增 ——
    "stitch",
)
CHANNEL_FIELDS = (
    "index", "name", "light", "ex", "em", "color",
    "black", "white", "visible", "role", "vmax",
)
```

| 来自 | 字段 |
|---|---|
| P0-4 | `range_mode`（`"global"` / `"per_frame"` / `"ref"`）、`ref_frame` |
| P1-5 | `proj_mode`、`proj_from`、`proj_to` |
| P1-6 | `rois`（ROI 列表，见 4.8.2） |
| P1-9 | `stitch`（tile 来源与布局，见 4.22.1） |
| P0-3 | `z_declared_manual`（用户手工声明过"Z 栈/时间序列"，见 3.18.3） |

**不入盘的运行时字段**（不是"坑"，它们本来就不是 dataclass 字段，白名单机制天然排除）：

| 字段 | 原因 |
|---|---|
| `_cache` | 整个 `(F, C, Y, X)` numpy 数组，几十 MB 到几百 MB |
| `_preview` | 同上，预览缓存 |
| `_ranges_ready` | 内部标记，读回像素时会重建 |
| `_cache_key` | 由处理链推导，读了就会重算 |

**向前/向后兼容**：载入时把白名单之外的未知字段原样收进 `item._extra`，保存时写回。
这样"用新版本打开过、再用旧版本打开"不会静默丢字段（迁移期尤其重要）。

#### 3.4.4 保存时机

| 场合 | 行为 |
|---|---|
| 首次保存 | 弹"另存为"，默认文件名 `未命名.icproj` |
| Ctrl+S | 有路径则原地覆盖；无路径则另存为 |
| Ctrl+Shift+S | 另存为 |
| 自动保存 | 写 `config/autosave.icproj`，条件：距上次自动保存 ≥ 120 s **且** 有改动（脏标记） |
| 自动保存触发的动作 | 导入完成、裁剪框提交（`box_committed`）、标定赋值、导出完成、分组变化、改通道设置 |
| 正常退出 | 若脏 → 静默写 autosave，再关 |
| 崩溃/断电 | 下次启动检测 `autosave.icproj` 存在且比上次正常退出新 → 弹"恢复了上次未保存的工作，是否载入？" |

写入方式：**先写 `.tmp` 再 `os.replace()`**，避免写一半断电产生损坏文件。

#### 3.4.5 打开与恢复

1. 读 JSON，校验 `app` 字段，不匹配则拒绝并提示。
2. `schema` 高于当前支持 → 拒绝，提示"工程由更新版本创建"。
3. `schema` 低于当前 → 走迁移函数链。
4. 重建 `Group` / `ImageItem` / `Channel` 对象。
5. **路径校验**：逐个 `os.path.exists(item.file_path)`。
   - 全部存在 → 直接打开。
   - 有缺失 → **弹面板列出缺失文件**（路径 + 是否同目录下找到了同名文件），给三个选项：**全部保留占位**（缺失条目显示为灰色缩略图，鼠标悬停提示"原文件不存在"）/ **逐个选择新位置** / **移除这些条目**。
   - **绝不能因为一个坏路径导致整个工程打不开。**
6. **不要自动重新探测元数据**（几十张大图会卡几十秒）。信任存储值。提供一个显式按钮「重新探测元数据」放在工程菜单里。
7. 恢复 `view` 状态。
8. 相对路径：同时存绝对路径和相对路径。

```json
{
  "path": "D:/frap/exp1/a.czi",
  "rel": "exp1/a.czi",
  "rel_base": "D:/frap"
}
```

打开时先试 `path`，失败则试 `rel_base` 手工重定位或 `工程文件所在目录 + rel`。**这一条是"整个文件夹拷到另一台电脑还能打开"的关键。**

#### 3.4.6 三个实现坑（必读）

**坑 1（R1 写错了，已更正）—— 白名单的理由是"schema 可控"，不是"asdict 会崩"。**

R1 说 `asdict()` 会把 `_cache` 抓出来导致崩溃/膨胀，**实测不成立**：

```
ImageItem 的 dataclass 字段（14 个）：path name group umpp calib width height
                                       frames bits channels note series group_manual group_key
_cache / _preview 是不是字段：False False
asdict() 结果能直接 json.dumps：能，910 字符（0.9 KB）
```

`_cache`、`_preview` 是**没有类型注解的普通属性**，不是 dataclass 字段，`asdict()` 根本不碰它们。

→ **仍然用 3.4.3 的显式白名单**，但理由是：字段集合必须可控、迁移点必须明确；
不是"不用就会崩"。别在这上面做无谓的防御（比如写自定义 JSON encoder），那会浪费时间还引 bug。

**坑 2 — `Group._seq` 计数器会撞 key。**
`Group.__post_init__` 用 `getattr(Group, "_seq", 0) + 1` 生成 `key`。启动时计数器是 0。载入工程后如果新建组，会生成 `k1`、`k2`……**和工程里已有的 key 冲突**，`_regroup()`（`main_window.py:1537`）按 key 匹配会把图放错组。
→ 载入后必须把计数器推到最大值之后：

```python
max_seq = 0
for g in groups:
    if g.key.startswith("k") and g.key[1:].isdigit():
        max_seq = max(max_seq, int(g.key[1:]))
Group._seq = max_seq
```

**但只做这一步还不够（R2 补充）**：推计数器只挡住了"新建组撞已有 key"这一种情况。
工程文件可能来自别的机器、被手工编辑过、或者包含非 `k<数字>` 形式的 key，所以载入时还要：

1. **校验 key 唯一性**：重复的 key 重新分配（并记一条日志）；
2. **兼容任意形式的 key**：不能假设一定是 `k<数字>`；不是这个形式的就把 `_seq` 往后推一位即可；
3. 更稳的做法（推荐）：把 key 的生成改成**带随机后缀**（如 `k1-7f3a`），
   从根上消除"计数器重置"这类跨会话问题，代价只是组名不可读（key 本来也不给用户看）。

**坑 3 — 多序列条目的 `path` 带 `#N` 后缀。**
LIF 第 2 个序列的 `path` 形如 `xxx.lif#2`，`ImageItem.file_path` property 负责剥掉。存原始 `path` 字符串 + `series` 字段，读回来一致。**不要"清洗"这个后缀**，否则 `series` 和 `path` 会对不上。

### 3.9 问题

12bit / 16bit 的原始数据经过"黑点白点归一化 → 8bit"之后：

- **定量信息永久丢失**。像素值不再与光子计数成正比，无法据此测强度、算比值、做共定位。
- **不可重新调窗**。以后发现对比度调过头了，没有原始数据可以重来。
- **不符合发表规范**。期刊和合作者索要原始数据时交不出东西。
- **TIFF 里连标定都只写了 `resolution` tag**（`_save` 的 `resolution=` 参数），没有 OME-XML，别人拿到图不知道通道是什么、激发发射波长是多少。

### 3.10 目标

新增"原始位深导出"，与现有合成彩图导出并列，两者可同时勾选。原始导出**不烘焙显示区间、不放大、不降位深**。
（R2 补充：导出的是**链后**数据——见 3.11.7；同时把可精确还原的链前数据内嵌在同一个 TIFF 里。）

#### 3.11.7 与处理链的关系：链后导出 + 可精确还原（R2 新增，N2 + N3）

R1 完全没写这一节。配准 / 背景扣除 / 去卷积都会改像素值，所以必须先定死两件事。

**N2：原始位深导出 = 链后。** 导出的像素与**界面上看到的、P1-6 定量算的**是同一份数据，
不会出现"看着一个样、导出另一个样"。

**N3：导出件必须能精确回到初始状态。** 实现方式**不是**做数学逆运算，而是
**在同一条 TIFF 里内嵌一份链前数据**：

| 位置 | 放什么 |
|---|---|
| 主页面（IFD 0） | **链后**数据：`uint16`（或 `float32`，见 3.11.2）、未放大、未降位深、显示区间未烘焙 |
| OME-XML `ImageDescription` | **人能读**的处理记录一句话，例如 `Processed by Image capture 1.2: register(pass), bg(percentile p=5.0)` |
| 私有 tag `65000` | **机器读**的处理记录：`process` 链的 JSON（kind + params + 参数版本 + 参考帧），UTF-8 |
| 私有 tag `65001…` | **链前数据**：zlib 压缩的"裁剪区域内、处理链之前"的原始像素（分块，见下） |

**为什么不做逆运算**（写进代码注释，避免以后有人"优化"掉）：

1. **亚像素平移不可逆**：`warpAffine` 正向插值一次、反向再插值一次 ≠ 原图（会糊一点点）；
2. **背景扣除后 clip 到 0 就不可逆**：负值信息已经丢了；
3. **去卷积本质不可逆**。

所以"精确还原"只能靠内嵌链前数据；处理记录仍然要写（用户要看"做过哪几步"，
合作者要照参数复现）。两者缺一不可。

**重新导入时的行为**：

1. 检测到 `65000` → 该图的 `calib` 后面追加 `（带处理记录）`，信息条上给一个按钮
   **「还原到未处理状态」**；
2. 点它就换成 `65001` 的链前像素**（逐像素相同）**，并恢复链前记录的 `umpp`；
3. 只有 `65000` 没有 `65001` 时（用户关掉了内嵌开关）→ 按钮置灰，
   tooltip 说明"这个文件只记录了处理步骤，没有内嵌原始数据"。

#### 3.11.8 内嵌数据的规格与边界（R2 新增）

| 项目 | 规定 |
|---|---|
| tag id | `65000` = 处理记录 JSON；`65001`、`65002`… = 链前数据分块 |
| tag 类型 | `BYTE`（tifffile 写 `extratags=[(65000, "B", len(blob), blob, True)]`） |
| 头部 | 每个数据块前 32 字节小端头：magic `ICRAW1` + `dtype` 代码 + `C` + `H` + `W` + crc32 |
| 分块 | 单块 ≤ 1 GB（TIFF 的 tag 值偏移是 32 位）；超了顺延到下一个 tag id |
| 压缩 | zlib（与现有 `_save` 的 `compression="zlib"` 一致） |
| 何时写 | **处理链非空**且用户没关掉「导出时内嵌可还原的原始数据」（**默认开**） |
| 处理链为空时 | **一个字节都不写**（不产生额外体积） |
| 体积预估 | 界面在勾选后立刻显示预估（如"约 +18 MB"），让用户有预期 |
| 超限兜底 | 链前数据 > 8 GB 时：不内嵌，改为"只写处理记录"，并在报告里明确标注"未内嵌原始数据，无法精确还原" |
| **禁止** | 不允许生成 `.icraw` / sidecar / 第二种专有文件。**本软件唯一的专有格式是 `.icproj`** |

**对外兼容性**（必须实测）：私有 tag 对 Fiji / Bio-Formats / Imaris 是未知 tag，会被忽略，
不影响它们打开主页面。如果实测发现某个软件会因为大私有 tag 报错，就退回到
"只写处理记录"（`65000`，很小）——**绝不能为了还原能力牺牲通用可读性**。

### 3.12 边界与异常

| 情况 | 处理 |
|---|---|
| 未标定（`umpp <= 0`）且勾了原始导出 | **允许导出**，只是不写 OME 物理尺寸；报告中标注"未标定：已导出像素，未写 PHYSICALSIZE"（R2 修正） |
| 已勾 OME 但 `tifffile` 写元数据失败 | 降级为不写 OME 的普通 TIFF，报告中标注 |
| 输出格式选了 PNG/JPG 但勾了原始导出 | **原始导出强制 TIFF**（PNG/JPG 不支持 16bit 灰度 + OME），并在界面提示 |

| 处理链非空 + 内嵌开关打开 | 主页面写链后、私有 tag 写处理记录与链前数据（见 3.11.7/3.11.8） |

## P0-3 Z 与 T 分离建模 `[待评审]`

### 3.15 现状（代码事实）

| 位置 | 事实 |
|---|---|
| `core/loader.py:73` `_probe_oib` | 只从 `f.axes` 里取 `"T"`：`if "T" in axes: item.frames = shape[axes.index("T")]`，**Z 完全不读** |
| `core/loader.py:182` `_probe_czi` | `item.frames = T × Z` |
| `core/loader.py:258` `_probe_lif` | `item.frames = T × Z` |
| `core/loader.py:355` `_canonical` | 5D `(T,C,Z,Y,X)` → transpose `(0,2,1,3,4)` → `reshape(t*z, c, y, x)`，**Z 被展平进帧维** |
| `core/loader.py:508` `_load_oib` | `ndim == 4` 时判断 `arr.shape[:2] == (c_meta, t_meta)` → 见下方 `待实测` |
| 文档 1 节 | "**时间序列 / Z 层**统一按「帧」处理" —— 这是当前明示的设计选择 |
| `main_window.py:777` | 只有**一个**帧滑条 `self.frame_slider`，标签"时间序列" |
| `model.py:112` | `frames: int = 1`，没有 Z 相关的任何字段 |

**`待实测`（我按代码推演的结论，需你跑一张 Z 栈 OIB 确认）**：
OIB 的 Z 栈 axes 是 `"CZYX"`。此时 `t_meta = None`（因为 `"T" not in axes`），`_load_oib` 里 `arr.shape[:2] == (c_meta, t_meta)` 变成 `(C, Z) == (C, None)` → **恒为 False** → 数组保持 `(C, Z, Y, X)`。但 `load_stack()` 之后一切消费者都按 `(T, C, Y, X)` 解释它，于是 **Z 层被当成时间帧、通道数被当成 Z 层数**。界面会出现"N 个通道"的错乱。
TIFF 的 4D 分支（`loader.py:536`）用的是 `if arr.shape[0] > arr.shape[1]: transpose` 这种启发式，同样会判错。

### 3.16 问题

1. Z 步进（µm）完全没读 —— 拿不到 Z 方向的物理尺度，无法做 3D、无法按物理比例显示正交视图。
2. Z 和 T 混在一个滑条里，用户无法区分"第 5 层"和"第 5 个时间点"。
3. 导出时"第 12 帧"语义模糊。
4. 上述 OIB/TIFF 的维度误判是**实际会出错的 bug**，不是体验问题。

### 3.17 目标

T 与 Z 分离计数、分离显示、分离选择；读 Z 步进；修复维度误判。

### 3.18 设计

#### 3.18.1 数据结构

`ImageItem` 新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `t_count` | int = 1 | 时间点数 |
| `z_count` | int = 1 | Z 层数 |
| `z_step_um` | float = 0.0 | Z 步进（µm），0 = 未知 |
| `t_interval_s` | float = 0.0 | 时间间隔（s），0 = 未知 |
| `z_range_um` | 派生属性 | `(z_count - 1) * z_step_um` |
| `frames` | int = 1 | **保留**，值 = `t_count * z_count`，兼容所有旧代码 |

**关键设计决定：内存里仍保持 `(F, C, Y, X)`，`F = T*Z`。** 这样 `compose()` / `crop_*` / `export_item` / 缩略图全部不用改。只新增两个索引换算：

```python
def flat_index(self, t, z):
    """T 主序、Z 次序 —— 与现有 _canonical 的 reshape 顺序一致，保持兼容。"""
    return t * self.z_count + z

def tz_of(self, f):
    return divmod(f, self.z_count)
```

**顺序必须按 `t * z_count + z`**，因为 `_canonical` 里 `transpose(0,2,1,3,4)` 之后 `reshape(t*z, ...)` 就是这个顺序。写成 `z * t_count + t` 会让所有已有数据错位。

需要 Z 投影时再临时 reshape 成 `(T, Z, C, Y, X)`。

#### 3.18.2 各格式的 Z / T 读取

| 格式 | T 数量 | Z 数量 | Z 步进 | 备注 |
|---|---|---|---|---|
| OIB/OIF | `axes` 含 `"T"` 时取 | `axes` 含 `"Z"` 时取 | `mainfile["Axis 3 Parameters"]` 的 `StartPosition`/`EndPosition`（单位米）`待实测` | 同时修 3.15 的维度误判 |
| CZI | `size["T"]` | `size["Z"]` | XML `<Scaling><Distance Id="Z"><Value>`，单位米（与现有 X 的读法一致，`loader.py:194`） | |
| LIF | `sizes["T"]` | `sizes["Z"]` | `im.coords["Z"]` 相邻差分 ×1e6；退化时读 XML `DimensionDescription DimID="3"` | |
| TIFF/OME | OME 的 `SizeT` | OME 的 `SizeZ` | OME 的 `PhysicalSizeZ` | **必须按 OME 的 `DimensionOrder` 重排维度**，不能用 `shape[0] > shape[1]` 猜 |
| 无元数据的多页 TIFF | `n_frames` | 1 | 0 | 见 3.18.3 手动声明 |
| PNG/JPG/BMP | 1 | 1 | 0 | |

**加一条硬规则**：所有读进来的数组，先按元数据声明的维度顺序**显式重排**到 `(T, C, Z, Y, X)`，再交给 `_canonical`。删掉 `_load_oib` / `_load_raster` 里那些 `shape[:2] == (...)`、`shape[0] > shape[1]` 的启发式判断——它们是不可靠的，改成"元数据优先，元数据缺失时用保守默认 + 界面可纠正"。

#### 3.18.3 无元数据时的手动声明（重要）

相机拍的 Z 序列 TIFF、从别处导出的多页 TIFF，没有任何维度信息。现状是硬当时间序列处理。

新增：中间信息条上加一个胶囊控件 **「多帧 = Z 栈 / 时间序列」**。

**显隐判据（R2 修正 —— R1 的判据会让控件自己消失）**：

R1 写的是"仅当 `frames > 1` 且 `z_count == 1` 时显示"。这是错的：用户一旦选了"Z 栈"，
`z_count` 就变成 `frames`，条件立刻不成立 → **胶囊消失，再也改不回去**。

正确判据：**"元数据没有给出 Z 信息"**，与控制变量无关：

```python
show = (item.frames > 1) and (item.z_step_um <= 0) and not item.z_meta_declared
# z_meta_declared = 读取元数据时确实声明了 Z 维度（CZI/LIF/OIB 的 Z、
#                   OME-TIFF 的 SizeZ>1 或 DimensionOrder 含 Z）
```

即：**元数据说得清就别打扰用户；元数据说不清才让他自己声明**。
一旦手工声明过，`z_declared_manual = True` 记在 `ImageItem` 上并进工程文件，
胶囊保持显示（供随时改回去），只是内容变成"已声明：Z 栈"。

- 选"Z 栈" → `z_count = frames, t_count = 1`
- 选"时间序列" → `t_count = frames, z_count = 1`
- 该选择记在 `ImageItem` 上（`z_declared_manual` + `t_count`/`z_count`），进工程文件

这一步成本很低（只是改两个整数），但能解决大量实际问题。

### 3.25 设计

#### 3.25.1 修复 estimate_ranges（先做，独立且必须）

```python
for c in range(c_count):        # 原来是 min(c_count, 3)
    ch = stack[0, c][::step, ::step].astype(np.float32)
    hi = float(np.percentile(ch, 99.8))

```

同时 `_auto_ranges`（`loader.py:480`）里 `ch.vmax = max(16.0, float(top))` 对第 4+ 通道也能拿到真实最大值，滑条范围就正确了。

去掉 `while len(out) < stack.shape[1]: out.append((0.0, 255.0, 255.0))` 这个兜底（不再需要），改为按 dtype 的满量程兜底。

#### 3.25.2 通道行的批量菜单

每个通道行右侧加 `⋯` 菜单：

| 菜单项 | 作用范围 |
|---|---|
| 应用到本组所有图（同通道序号） | `cur_group.images` |
| 应用到同 µm/px 的所有图 | 跨组，按 `round(umpp, 4)` 匹配 |
| 应用到所有组 | `self.items` 全部 |
| 复制本通道设置 | 写入剪贴板（应用内 `self._clip_channel`） |
| 粘贴到其他通道 / 其他图 | 从剪贴板 |
| 重置为自动区间 | 单张，重新跑 `estimate_ranges` |

**匹配规则（关键设计决定，避免误伤）：**

1. 优先按**通道序号 `index`** 匹配。
2. 匹配后校验 `role` 是否一致（`gray` / `green` / `rgb`）；不一致则跳过该图该通道。
3. 目标图通道数不足 → 跳过。
4. 状态栏报告：`已应用到 18 张图的 CH2，跳过 2 张（通道类型不一致）`。**必须报告跳过数量**，静默跳过会导致用户以为都应用了。

**颜色 vs 区间的差异：**

- 显示区间（`black` / `white`）：不同通道的强度分布可能差好几个数量级，**批量应用会压死弱信号通道**。所以批量应用区间时给出警告提示："不同图像的信号强度可能不同，批量应用区间可能导致部分图过曝/过暗。建议先应用到本组。"
- 配色（`color`）：批量应用是安全的，**不受上面警告限制**。

#### 3.25.3 时间序列归一化

在「通道与颜色」卡片顶部加一组控件：

| 控件 | 选项 | 说明 |
|---|---|---|
| 区间模式 | **统一区间**（默认，= 现状）/ 逐帧自动 / 按参考帧 | |
| 分位数 | 黑点分位 / 白点分位 | 默认 55 / 99.8，与 `estimate_ranges` 一致 |
| 参考帧 | 第 1 帧 / 手动指定 | 仅"按参考帧"模式可用 |

| 模式 | 算法 |
|---|---|
| 统一区间 | 一帧算出区间，全部帧共用（现状） |
| 逐帧自动 | 每帧独立按分位数算黑白点。抗漂白效果最好，但会掩盖真实的强度下降（**必须提示**："逐帧归一化会消除强度随时间变化的真实信号，定量分析时请勿启用"） |
| 按参考帧 | 以参考帧的区间为基准，逐帧算自己的分位位移量，把区间整体平移过去。保留相对强度差异，同时修正漂白导致的整体变暗 |

**计算实现要点：**
- 逐帧分位数是 `frames × channels` 次 `np.percentile`，60 帧 × 3 通道在大图上会明显卡 → **必须抽样**（沿用 `step = max(1, max(h,w)/512)`）+ **走后台线程** + 结果缓存在 `item` 上（key 含参考帧号）。
- 只影响**显示和合成彩图导出**。**原始位深导出不受影响**（与 P0-2 一致，这一条要在两处代码里都写清楚，避免以后被改坏）。

#### 3.25.4 配色方案（可选）

「通道与颜色」卡片顶部加"配色方案"下拉：默认 / 灰底+绿+红 / 灰底+蓝+红 / 灰底+品红+绿 / 自定义…。选择后一次性套用到当前组。自定义方案存进 `.icproj` 的 settings 段。

### 3.26 边界与异常

|---|---|

## P1-5 Z 投影 + 正交视图 `[待评审]`

### 4.1 现状

无任何实现。`loader.py` 把 Z 展平进帧维（P0-3），所以现在连"哪些帧属于同一层 Z"都不知道。

### 4.2 目标

Z 投影（MIP 等）+ XZ/YZ 正交视图，成果能进导出流程，物理尺度正确。

### 4.3 设计

#### 4.3.1 投影

新建 `core/project.py`：

```python
def project_z(stack, z_from, z_to, mode):
    """stack: (F, C, Y, X)，F = T*Z。返回 (C, Y, X)。
    mode: "max" | "sum" | "mean" | "sd"
    """
```

- `stack` reshape 成 `(T, Z, C, Y, X)`，取 `t` 与 `z_from..z_to` 的切片，按 mode 归约。
- **分块实现**：Z 层数多、图大时（如 21 层 × 8000×8000）不能一次性 reshape 出 5D float 数组。约束：单次处理的像素数 ≤ 4×10⁷（与 `compose()` 的 `band` 逻辑同量级），超出则按 Y 方向分条。

投影模式：

| 模式 | 用途 |
|---|---|
| MIP（最大强度） | 最常用，看结构全貌 |
| Sum（求和） | 定量（总荧光量） |
| Mean（平均） | 降噪 |
| SD（标准差） | 看变化区域（进阶） |

投影范围：全部 / 当前层 ± n / 手动起止层（两个输入框）。范围记在 `ImageItem` 上（`proj_mode` / `proj_from` / `proj_to`）。

**与裁剪、标尺的关系（关键）**：投影只改变 Z 维度，**XY 物理标定不变 → 裁剪框、标尺、导出流程完全复用**。这是把投影做成"帧维归约"而不是"新对象"的原因，改动面最小。在 `load_stack()` 之后、`compose()` 之前插入投影步骤即可。

**投影何时生效：**

| 场合 | 行为 |
|---|---|
| 界面预览 | 投影结果作为当前显示的一帧（帧滑条/时间滑条进入"投影模式"，显示为灰态或隐藏 Z 行） |
| 导出 | 「导出内容」里加"Z 投影图"，输出 `stem_crop_MIP.tif`；`DimensionOrder` 变为 `XYCZT` 且 `SizeZ = 1` |

#### 4.3.2 正交视图

| 项目 | 规定 |
|---|---|
| 取样线 | 在画布上按住 Alt 拖出一条虚线（或右栏「正交视图」卡片里点"画取样线"）；只允许水平线（XZ）或垂直线（YZ），或任意角度（进阶：沿任意方向重采样，不做） |
| 面板 | **独立浮动窗口**（不是右栏卡片，因为需要正方形区域看剖面） |
| 内容 | 沿取样线抽取的 `(Z, L)` 剖面图，`L` 是沿线长度。可用各通道自己的配色叠加显示 |
| 物理比例 | Z 方向用 `z_step_um`，L 方向用 `umpp`。**Z 步进未知时不按物理比例显示，改为等距拉伸，并在面板上标注"Z 步进未知，未按比例显示"** |
| 交互 | 拖动取样线，剖面实时更新（100 ms 节流）；面板上滚轮缩放，双击复位 |
| 导出 | 正交视图可单独导出 PNG/TIFF（8bit 或原始位深），带两轴标尺（L 轴用 µm，Z 轴用 µm） |
| 多通道 | 默认显示当前可见通道的叠加；单个通道可切换 |

### 4.4 边界与异常

| 情况 | 处理 |
|---|---|
| `z_count == 1` | 投影与正交视图入口置灰，tooltip 提示"这张图只有一层 Z" |

## P1-6 定量分析（ROI / 线剖面 / 共定位 / 粒子计数） `[待评审]`

### 4.7 目标

让软件能**量出数字**。做最小可用集，不做完整 ImageJ。

### 4.8 设计

#### 4.8.1 铁律（写进代码注释）

> **所有统计分析必须读取原始位深数据，不得读取合成后的 8bit RGB 图。**
> 显示区间、逐帧归一化、通道配色、屏幕锐化（`sharpen_display`）一律不参与计算。
> 若启用了处理链（配准/背景扣除/去卷积），则读取处理链重建后的数据，并在结果表里标注已启用的步骤。

#### 4.8.2 ROI 数据结构

```python
@dataclass
class Roi:
    rid: str
    kind: str                      # "rect" | "ellipse" | "polygon" | "freehand" | "line"
    points: list                   # 归一化到「原图整帧」的坐标 [[nx,ny], ...]，0~1
    z: int = -1                    # -1 = 跟随当前 Z 层；>=0 = 锁定层
    t: int = -1                    # -1 = 跟随当前时间点
    ch: int = -1                   # -1 = 所有可见通道
    label: str = ""
```

**坐标基准的决策：归一化到原图整帧（0~1），不相对裁剪框。** 理由：这样换 Z 层、换时间点、改裁剪框位置、改缩放都不影响 ROI 的位置语义；导出到正交视图或投影图也能直接换算。

ROI 挂在 `ImageItem` 上（不挂组），进 `.icproj`。

#### 4.8.3 工具集（最小可用）

| 工具 | 交互 |
|---|---|
| 矩形 | 拖拽 |
| 椭圆 | 拖拽 |
| 多边形 | 逐点点击，双击闭合 |
| 手绘 | 按住拖动，松开闭合 |
| 直线 | 拖拽（用于线剖面和长度测量） |
| 复制 / 删除 | 选中后 Ctrl+C / Delete；ROI 列表可批量管理 |

**明确不做**：魔棒、阈值自动分割、机器学习分割。

UI：右栏加「ROI 与测量」卡片，列出所有 ROI（名称可改），底部按钮：新建 / 删除 / 全部导出 CSV。画布上叠加显示 ROI 轮廓（半透明填充 + 编号）。

#### 4.8.4 统计输出字段

对每个 ROI × 每个可见通道：

| 字段 | 公式 | 说明 |
|---|---|---|
| `Area_px` | 掩膜内像素数 | |
| `Area_um2` | `Area_px × umpp²` | 未标定时为空 |
| `Mean` | 均值 | 原始位深 |
| `SD` | 标准差 | |
| `Min` / `Max` | | |
| `Median` | | |
| `IntDen` | `Mean × Area_px` | 积分密度 |
| `RawIntDen` | 像素值之和 | |
| `Mean_bg_corr` | `Mean − bg_mean` | 需先设背景 ROI |
| `IntDen_bg_corr` | `(Mean − bg_mean) × Area_px` | 最常用于比较荧光强度 |

> **`IntDen` 的口径（R2 补注）**：按 ImageJ 的定义，`IntDen = Mean × 面积（像素数）`，
> **与有没有标定无关**——未标定只是 `Area_um2` 留空，`IntDen` 照算不误。
> 实现时别把它当物理量、也别因为未标定就返回空值（Fiji 用户会立刻发现对不上）。

背景定义：优先做**手动背景 ROI**（用户画一个 ROI 标记为背景，其余 ROI 自动扣它的均值）。这是最不容易出错的做法。全图百分位扣背景作为备选。

#### 4.8.5 线剖面

| 项目 | 规定 |
|---|---|
| 输入 | 一条直线 ROI（两个点） |
| 采样 | 沿线等距取 `max(2, 线长像素数)` 个点，双线性插值（**不要最近邻**，会阶梯状） |
| 宽度 | 可选，取垂直方向 ±n 像素的平均，抗噪 |
| 输出 | `(距离 µm, 强度)` 数组 + 图上叠加曲线图。**必须用 QPainter 自绘折线** —— 开发环境里确实装了 matplotlib，但**发布包构建时会删掉它**（见附录 A）。照 R1 那句"用已打包的 matplotlib"写，开发机一切正常、**发出去就崩** |
| 导出 | CSV（两列）+ PNG |
| 多通道 | 同一剖面上叠加多个通道的曲线，各自配色 |

#### 4.8.6 共定位

对两个指定的通道（或 ROI 内）：

| 指标 | 公式要点 | 阈值参数 |
|---|---|---|
| Pearson r | 标准皮尔森相关系数 | 无 |
| Manders M1 / M2 | `Σ(A_i where B_i>thrB) / ΣA_i`，M2 对称 | **必须给阈值**，界面提供 Otsu / 手动 / 百分位 |
| Overlap coefficient | `Σ(A_i·B_i) / sqrt(ΣA_i²·ΣB_i²)` | 无 |
| Costes 移位检验 | 进阶，可选 | |

**前置校验（必须做）**：界面在算共定位前检查两通道的配准状态（P1-7）。未配准则弹出提示："两通道尚未配准，共定位结果可能不可靠。建议先在「处理」卡片里做通道配准。" —— 允许用户坚持继续，但结果里要标注"未配准"。

**明确不做**：Costes 自动阈值迭代（计算量大且容易误导），FRET/FRAP 动力学拟合，荧光寿命。

#### 4.8.7 粒子计数

管线（全部用 cv2，不依赖 scipy）：

```python
gray = roi 区域原始数据归一化到 uint8 或直接用 float
th = cv2.threshold(...)            # Otsu / 手动 / 百分位
th = cv2.morphologyEx(th, cv2.MORPH_OPEN, kernel)     # 去噪点
th = cv2.morphologyEx(th, cv2.MORPH_CLOSE, kernel)    # 填小洞
n, labels, stats, centroids = cv2.connectedComponentsWithStats(th)
# 按面积 / 等效直径过滤
# 粘连粒子：cv2.distanceTransform + cv2.watershed（可选开关）
```

输出：每个粒子的 `Label` / `Centroid_px` / `Centroid_um` / `Area_px` / `Area_um2` / `EqDiameter_um` / `MeanIntensity`。

参数：阈值方法、形态学核大小、面积下限/上限（µm²）、是否启用分水岭分离。**所有参数记在 ROI 上，进工程文件。**

#### 4.8.8 结果表与导出

- 独立对话框（不用右栏，表格需要宽度）：`QTableWidget`，行 = ROI × 通道，列 = 统计量。
- 工具栏：复制到剪贴板（TSV，直接粘进 Excel）/ 导出 CSV / 只导出选中行。
- CSV 用 `utf-8-sig` 编码（Excel 打开中文表头不乱码）。
- CSV 头部写入元信息注释行：图片名、µm/px、ROI 坐标基准、启用的处理步骤、是否配准、时间戳。**这是方法学可追溯性的最低要求。**

### 4.9 边界与异常

| 情况 | 处理 |
|---|---|
| 未标定（`umpp == 0`） | 面积只给 `Area_px`，`Area_um2` 留空，提示"未标定，无法给出物理面积" |
| ROI 超出图像边界 | 存在时不报错，计算时只取交集，并在结果里标注"部分在界外" |
| ROI 面积 < 3 像素 | 提示"ROI 太小，统计无意义"，仍给出结果 |
| 图像是 `role == "rgb"` 的合成图 | 允许测量，但结果里标注"测量的是已合成图，不是原始通道数据" |
| 粒子计数阈值为 0（全黑） | 返回 0 个粒子，不崩 |
| 大图 + 大 ROI | 只对 ROI 的包围盒取数据（`frame_data[:, y0:y1, x0:x1]`），不整帧计算 |

### 4.10 影响文件

`core/analysis.py`（新建）、`core/roi.py`（新建，ROI 定义与序列化）、`ui/roi_panel.py`（新建）、`ui/roi_dialog.py`（新建，结果表）、`ui/canvas.py`（ROI 绘制与交互，改动较大）、`core/model.py`（`ImageItem.rois`）、`ui/main_window.py`（菜单入口 + 状态栏）。

### 4.11 验收标准

1. 在 12bit CZI 上画一个矩形 ROI → Mean 与 Fiji 同一 ROI 的 Mean 一致（误差 < 0.5%）。**这是最重要的验收项，用来证明没读错数据源。**
2. 把显示区间黑点白点大改 → ROI 的 Mean **不变**（证明统计没经过显示区间）。
3. 画背景 ROI + 信号 ROI → `IntDen_bg_corr` 等于手工算的值。
4. 画一条跨边界直线 → 剖面曲线横轴是 µm 且与 ROI 长度一致；导出 CSV 两列可用。
5. 两个通道做共定位：故意错开 5 像素 → Pearson r 明显下降；未配准时出现提示。
6. 粒子计数：在一张已知数量的合成测试图（如 37 个点）上给出一致的计数（±1）；调面积下限能过滤掉噪点。
7. 导出 CSV → Excel 打开中文列名不乱码；注释行含 µm/px 与处理链信息。
8. 换 Z 层 / 换时间点 → ROI 位置不变（归一化基准正确）。
9. ROI 定义保存进 `.icproj`，重开工程后 ROI 与参数完整恢复。

## P1-7 通道配准 + 背景扣除 + 漂移校正 `[待评审]`

### 4.12 目标

把多通道对齐、背景扣干净、时间序列锁住。**这是共定位与强度比较成立的前提。**

### 4.13 设计

#### 4.13.1 通道 XY 配准

用 cv2 的相位相关，**不需要 scipy**：

```python
# 1. 取两个通道的同一位面
# 2. 归一化到 float32，必要时加窗（Hanning）抑制边缘效应
# 3. shift, response = cv2.phaseCorrelate(ref, mov)
# 4. 亚像素位移 → 用 cv2.warpAffine 带 INTER_LINEAR 平移回去
```

| 参数 | 规定 |
|---|---|
| 参考通道 | 用户选择（默认通道 0，或信号最强的通道） |
| 自由度 | **只做平移**。旋转/缩放不做（共聚焦的通道失配主要是平移） |
| 亚像素 | `phaseCorrelate` 原生支持 |
| 前置处理 | 先做一遍高通（减去高斯模糊）再相关，避免大块背景主导结果 |
| 结果展示 | 界面上显示每个通道相对参考通道的位移：`CH2 相对 CH1：Δx = -1.3 px (-0.13 µm), Δy = +0.4 px` |
| 手动微调 | 允许用户在这组数值上再手动加偏移（±0.5 px 步进） |
| 抽查图 | 提供"叠加检查图"：参考通道用绿、目标通道用品红，错位会变成彩边。用户肉眼即可判断配准是否成功 |

**可选的进阶**（不在本次）：仿射配准（`cv2.estimateAffinePartial2D` + 特征点）。

#### 4.13.2 背景扣除

按实现成本排序，**本次做前两个，第三个可选**：

| 方法 | 实现 | 适用 |
|---|---|---|
| 常量扣除 | `data - c`，`c` 手动填 | 最简单，有明确暗电流值时用 |
| 百分位扣除 | `data - percentile(data, p)`，`p` 默认 5 | 通用于共聚焦（背景占大部分像素） |
| ROI 背景 | 用户指定背景 ROI，扣其均值 | 最严谨（与 P1-6 共用 ROI 机制） |
| Rolling ball | 形态学开运算近似（`cv2.morphologyEx` EX 核）或纯 numpy 实现 | ImageJ 用户的习惯，本次标记为**可选** |

负数处理：**保留负值**（`float32`），不要 clip 到 0。clip 会丢失背景估计的偏差信息。显示时由显示区间决定可见范围。

#### 4.13.3 时间序列漂移校正

逐帧相对参考帧（默认第 1 帧）做平移配准，累积位移写进处理链。参考帧可手动指定。

**注意**：漂移校正后 `t_interval_s` 不变，只是 XY 锁定。

#### 4.13.4 处理链落地形式

```python
item.process = [
    ProcessStep("register", {"ref_ch": 0, "shifts": {"1": [1.3, -0.4]}, "manual": {}}),
    ProcessStep("bg",       {"mode": "percentile", "p": 5.0}),
]
```

- 界面上每步一行：`[开关] 通道配准 · CH2 位移 -1.3, +0.4 px` + `[重新计算]` + `[删除]`
- 处理链进 `.icproj`（P0-1）
- 缓存失效按 2.3 的指纹机制
- **预览即所见**：开启后画布立即显示处理后的结果
- 导出时处理链生效；导出报告里列出启用的步骤

#### 4.13.5 预览性能

配准/背景扣除是逐帧操作，60 帧的数据如果每次拖动滑条都重算会卡。

- 后台线程计算整条链的结果，**缓存处理后的帧**（不是只缓存一帧）。
- 内存约束：处理后的数据是 `float32`，8 倍于 `uint16`。60 帧 × 1024×1024 × 3 通道 × 4 字节 = 754 MB。**必须限制**：只缓存当前图 + 最近 3 张（LRU），或对大图只缓存当前帧 + 用低分辨率预览。
- 具体策略留待实现时按实测定，规范里约定**必须有内存上限，不能无限制缓存**。

### 4.14 边界与异常

| 情况 | 处理 |
|---|---|
| 单通道图 | 配准入口置灰 |
| 通道间信号强度差 1000 倍 | 相关前各自归一化，仍可能失败 → 提示用户手动填位移 |
| 配准得到的位移 > 图像尺寸的 20% | 判定为不可信，给出警告并要求用户确认（通常是通道认错了） |
| `result response` 很低 | 标注"置信度低"，提示手动检查 |
| 背景扣除后全为负 | 提示"背景估计过高"，给出建议参数 |
| 处理链导致缓存超限 | 按 LRU 释放；释放后重新计算（不报错） |

`core/register.py`（新建）、`core/model.py`（`process` 已在 P0-1 定义）、`core/loader.py`（`load_stack` 应用处理链 + 缓存指纹）、`ui/main_window.py`（新卡片「处理」）。

### 4.16 验收标准

1. 构造一张测试图：把某通道整体平移 (+3, -2) 像素 → 配准算出的位移在 ±0.3 px 内，配准后叠加检查图看不到彩边。

3. 百分位 5% 扣背景 → 背景区域均值接近 0；信号区域强度按预期下降。

8. 内存占用有上限（连续切换 10 张 4096×4096 的图，进程内存不持续增长）。

## P1-8 去卷积 `[待评审]`

### 4.17 客观评估

先说清楚：**CPU 上的去卷积是慢的，且参数不当会产生伪影。** 这一项的收益取决于你的实际数据（共聚焦光学切片质量、采样率是否达到 Nyquist）。如果数据本身采样不足，去卷积救不回来。

规范里把默认参数设保守，并且**明确标注"去卷积会改变像素值"**。

### 4.18 设计

#### 4.18.1 两条路线

| 路线 | 实现 | 依赖 | 状态 |
|---|---|---|---|
| A. Richardson-Lucy | 纯 numpy FFT（`np.fft.rfft2`），分块 + 迭代 | 无新增 | **本次必做** |
| B. ONNX 深度学习模型 | `onnxruntime` 1.30.0 已打包 | 需要模型文件 | **待拍板**（见附录 E） |

路线 B 的模型文件涉及**体积（几十到几百 MB）与许可**两个问题。建议本次只做路线 A，把路线 B 的接口预留（`ProcessStep("deconvolve", {"engine": "onnx", "model": "..."})`），模型等你确认来源后再接。

#### 4.18.2 PSF 来源

| 来源 | 优先级 | 说明 |
|---|---|---|
| 阅读器参数计算（高斯近似） | 默认 | 需要：NA、发射波长、像素尺寸、折射率。σ ≈ `0.21 × λ_em / NA / px_size`（做量级估计即可，不追求精确） |
| 实测 PSF | 可选 | 用户提供一张 bead 图或 PSF 文件，取质心附近区域 |
| 手填 σ | 兜底 | 一个数值输入框 |

**参数从哪里读**：NA 和发射波长目前**没有从元数据里读**（`_probe_*` 只读了通道名/激发/发射波长，没读物镜 NA）。所以要么先补读 NA（OIB 的 `Acquisition Parameters Common`、CZI 的 `<ObjectiveName>` 附近），要么让用户手填。**建议手填 + 记在工程里**，成本最低。

折射率：下拉（1.00 空气 / 1.33 水 / 1.38 甘油 / 1.52 油），默认 1.33。

#### 4.18.3 参数与默认值

| 参数 | 默认 | 范围 | 说明 |
|---|---|---|---|
| 迭代次数 | 10 | 1–50 | 超过 30 容易出伪影，界面提示 |
| 阻尼/正则 | 无 | 可选 | 有正则能抑制噪点放大 |
| 分块大小 | 自动 | | 按内存上限切 |
| 边界处理 | 分块重叠 16 px | | 避免块缝 |

#### 4.18.4 性能约束（硬规定）

- 对 1024×1024 → 10 次迭代在 CPU 上可接受（秒级）。
- 对 16000×16000 → **默认只对裁剪区域去卷积**，并且给出预估耗时提示。
- 必须分块 + 进度上报 + 可取消。
- 上限：单次处理像素数默认上限 4×10⁷，超出时提示并建议先裁剪。

#### 4.18.5 关于定量

去卷积**改变像素值**，因此：

- 启用去卷积后，P1-6 的统计结果读的是**去卷积后的数据**（处理链顺序决定）。
- 结果 CSV 的注释行必须写明"已启用去卷积（RL，10 次迭代，σ=…）"。**这是发表时审稿人会问的。**
- 界面上在启用去卷积时弹一次提示："去卷积会改变像素强度，同组数据的定量比较必须在相同参数下进行。"

### 4.19 影响文件

`core/deconvolve.py`（新建）、`core/model.py`（`process` 链加 `deconvolve` 步骤）、`ui/main_window.py`（处理卡片里加一段参数 UI）。

### 4.20 验收标准

1. 构造一张模糊的合成图（已知真值）→ RL 去卷积后与真值的 MSE 比模糊图低。
2. 迭代 10 次 vs 30 次 → 30 次更锐但噪点更多，界面给出提示。
3. 对 4096×4096 图去卷积 → 界面不卡死，有进度条，可取消。
4. 去卷积前后做 P1-6 的 ROI 统计 → 数值确实变化，且 CSV 注释行记录了去卷积参数。
5. 关闭去卷积开关 → 统计结果回到未去卷积的数值。
6. 未提供 NA/波长时 → 使用手填 σ，流程不中断。

### 4.22 设计

#### 4.22.1 三种场景分开处理

| 场景 | 识别方式 | 处理 |
|---|---|---|
| **单文件多 Scene（S）** | CZI dims 含 `S` 且 > 1 | 每个 Scene 出一个条目，命名 `文件名 · 场景 2/9`（复用 LIF 的多序列机制） |
| **单文件 tiled / Mosaic** | tile 位置元数据存在（CZI 的 `<TileRegion>` / 每 tile 的 `PositionX/Y`） | 按绝对位置拼接，出一个条目 |
| **多文件阵列** | 文件名含行列编号（`r01c02` / `_x03_y05` / `tile_3_5`） | 按解析出的坐标拼接；解析失败则进入手动排列界面 |

**对象模型**：拼接结果是一个新条目 `ImageItem`，额外带：

```python
stitch: dict = field(default_factory=dict)
# {"mode": "meta"|"phase"|"manual", "cols": 6, "rows": 8, "tiles": [...], "sources": [...]}
```

拼接结果进 `.icproj` 时**只存 tile 的来源路径与布局参数**，不存拼好的像素（几百 MB 的图不可能进工程文件），下次打开时按参数重新拼。这样打开工程会慢一点，但文件小。**这个取舍要确认**（见附录 E）。

#### 4.22.2 拼接算法

```
优先：元数据绝对位置（精确，零误差）
  ↓ 没有位置信息
重叠区相位相关（cv2.phaseCorrelate 求相邻 tile 的位移）
  ↓ 有位置但精度不够
以元数据位置为初值，用相位相关在 ±5 px 内微调
  ↓ 都失败
降级为"独立条目 + 提示"，不阻塞导入
```

**全局优化**：链式拼接会有累计误差。简单做法：先按元数据排列，若存在重叠则用重叠区做一次全局最小二乘修正（用 `cv2.estimateAffinePartial2D` 或直接平均位移残差）。**本次先做"元数据为主 + 相邻微调"**，完整全局优化标记为可选。

#### 4.22.3 内存与写入（关键约束）

上亿像素的拼接结果**不能整张驻留内存**（`_load_czi` 现在就是整读，这个习惯要改）。

- 逐 tile 读取 → 贴到输出画布 → 逐块落盘。
- 输出用 `tifffile` 的**增量写入**（`TiffWriter` + `write` 分块），或按 Y 方向分若干条带。
- 输出路径：直接写进 `output/` 或用户指定的临时目录，`ImageItem.path` 指向这个拼接结果文件，`stitch` 字段记来源。
- 内存上限：单次驻留 ≤ 4×10⁷ 像素。

#### 4.22.4 UI

- 拼接完成后出现条目 `文件名 · 拼接 6×8 · 12000×9000`。
- 提供一个"查看 tile 布局"小对话框：网格显示每个 tile 的缩略图与重叠量。
- 多文件阵列解析失败 → 提供一个"手动排列"对话框：把文件列表拖进网格，指定行列数与重叠率。
- 拼接结果**可以正常参与分组、裁剪、标尺、导出**（它就是一个普通 `ImageItem`）。

### 4.23 边界与异常

| 情况 | 处理 |
|---|---|
| 拼接后尺寸超过单张 200 MP 的建议上限 | 允许，但提示内存风险（与文档 14.1 一致） |
| tile 之间完全没有重叠 | 用元数据位置直接摆放，不尝试相关（相关会给出错误结果） |
| 重叠量 < 5% | 相位相关不可靠 → 提示并只用元数据位置 |
| 元数据位置缺失且无重叠 | 报错"无法确定 tile 相对位置"，要求手动排列 |
| 拼接磁盘空间不足 | 提前估算所需空间并检查，不足则拒绝并提示 |

### 4.25 验收标准

1. 一张多 Scene 的 CZI → 每个 Scene 出一个独立条目，命名正确，各自能裁剪导出。

### 5.2 问题

1. **竖标尺识别不了**（竖构图、竖版排版、部分软件导出的图）。
2. **斜标尺识别不了**。
3. **千分位数字解析错误**：`1,000 µm` 会被 `TOKEN` 匹配成 `1,000` → `1.000 µm`，**结果差 1000 倍**。这是静默错误，最危险。
4. 带边框/带刻度的标尺会被 `max(axis=0)` 并成一条错误的线。
5. 识别失败时只给一句文字原因，用户不知道该改什么。
6. 一个批次里识别错了，用户不会逐张核对（20 张图 × 1.3 s 的批量识别，出错了很难发现）。

### 5.3 目标

支持竖标尺、修复千分位、给出置信度与可视化、支持多候选选择。

### 5.4 设计

#### 5.4.1 方向支持（核心改动，成本低）

**关键取巧：不重写算法，把图转置后复用同一套逻辑。**

```python
def detect_umpp(rgb, try_both=True):
    res = _detect_oriented(rgb, orientation="h")
    if res["ok"] or not try_both:
        return res
    res_v = _detect_oriented(np.transpose(rgb, (1, 0, 2)), orientation="v")
    # 转置后 x/y 互换，坐标要换回来
    return _fix_coords(res_v)
```

- 第一轮（水平）成功就返回，**不跑第二轮** —— 90% 的图是横标尺，这样批量识别的平均耗时基本不变（避免"竖标尺支持"让所有图都慢一倍）。
- `_detect_oriented` 就是现有的 `detect_umpp` 主体，加一个 `orientation` 参数用于坐标换算。
- 返回结果里加 `orientation` 字段，供界面可视化用。

**注意转置的坑**：`np.transpose(rgb, (1, 0, 2))` 对 3 通道图是正确的；对灰度图（`rgb.ndim == 2`）要单独处理。现在的 `detect_umpp` 入参是 `quick_rgb()` 出来的 3 通道图（`render.py:189`），所以实际是 3 通道。

#### 5.4.2 斜标尺（用 cv2，成本可控）

因为 cv2 5.0.0 已打包，可以用 Hough：

```python
edges = cv2.Canny(gray_u8, 50, 150)
lines = cv2.HoughLinesP(edges, 1, np.pi/180, threshold=..., minLineLength=..., maxLineGap=...)
# 筛：长度足够 + 两端反差足够（是亮线或暗线）+ 附近有 OCR 数字
```

- **只在水平和垂直两轮都失败时**才跑 Hough（控制耗时）。
- 输出候选线的两个端点，方向可以是任意角度。
- **优先级排在最后**，标记为"实验性"，可在设置里关闭。

#### 5.4.3 修复千分位（必须做，独立小改动）

现状 `TOKEN` 里 `(\d+(?:[.,]\d+)?)` 会把 `1,000` 整体吃掉，然后 `.replace(",", ".")` 变成 `1.000`。

修复规则：

```
数字里同时出现 "." 和 "," → 按最后出现的那个作为小数点，另一个是千分位分隔符
只有 "," 且其后恰好 3 位数字，且前面有 1-3 位数字 → 判定为千分位（1000）
只有 "," 且其后不是 3 位数字 → 判定为小数点（欧洲写法 1,5 µm）
只有 "." 且其后恰好 3 位数字 → 歧义，按小数点处理（因为标尺数值不会是 "1.000"）
```

同时补两个兼容：

- 全角数字 `５μｍ` → 先做 `unicodedata.normalize("NFKC", text)` 归一化（能同时解决全角单位、全角数字、全角空格）。
- 无单位但有数字：`TOKEN` 要求必须带单位，所以 `500` 不会匹配。**保持这个行为**（避免把染色编号当标尺），但失败原因里要说明"读到数字但没有单位"。

#### 5.4.4 多候选与置信度

`detect_umpp` 返回结构扩展（**保持向后兼容**：`worker.py:54` 读的是 `res["ok"]` / `res["umpp"]` / `res["text"]` / `res.get("why")`，这些字段不能删）：

```python
{
  "ok": True,
  "umpp": 0.621,
  "text": "50 µm",
  "bar": {...},
  "why": "OCR 读数 + 标尺长度",
  # 新增
  "orientation": "h",              # "h" | "v" | "diag"
  "confidence": "high",            # "high" | "mid" | "low"
  "score": 0.87,                   # 0~1
  "candidates": [ {...}, {...} ],  # 最多 3 个，按 score 降序
}
```

置信度打分（加权）：

| 因子 | 权重 | 说明 |
|---|---|---|
| OCR 文本置信度 | 高 | RapidOCR 自带的 score |
| 线条反差 | 高 | `abs(level - back) / 满量程` |
| 线条长度占图宽比例 | 中 | 太短不可信 |
| 数字与线条的距离 | 中 | 越近越可信 |
| umpp 落在合理区间 | 门限 | 现有 `0.002 <= umpp <= 60`，越界直接丢弃 |

分级：`score >= 0.75` → high；`0.5 ~ 0.75` → mid；`< 0.5` → low。

`worker.job_calibrate` 根据分级改文案：

| 分级 | `item.calib` 文案 |
|---|---|
| high | `标尺识别 + OCR（读到 50 µm）` |
| mid | `标尺识别（读到 50 µm，建议核对）` |
| low | `待人工确认：识别置信度低（读到 50 µm）` |

#### 5.4.5 多候选交互

当 `len(candidates) > 1` **且**它们给出的 `umpp` 彼此差异 > 5% 时：

- 自动识别完成后，该图在左栏标一个橙色圆点。
- 点击该图 → 画布上叠加画出**所有候选线**（不同颜色 + 编号），旁边一个小面板列出候选：`① 50 µm · 长 80 px · 置信 0.87`。
- 用户点选后写入 `umpp`。

如果只有一个候选或候选之间差异很小 → 直接采用最高分，不打扰用户。

#### 5.4.6 识别结果可视化（这个最实用）

识别完成后，在**原图**上叠加绘制：

- 画出识别到的线段（粗线，与画面反差色）
- 在线段中点旁标注识别到的数字与算出的 µm/px
- 右上角标置信度徽标

旁边一个按钮 **「不对，手动框」** → 直接进入现有的画线标定模式（`on_line_mode`），并把识别到的端点作为初始线的两端（用户只需微调）。

**目前识别完什么反馈都没有，用户不知道软件画在哪了** —— 这是实际使用中最大的困扰，比竖标尺重要。

#### 5.4.7 性能

| 场景 | 处理 |
|---|---|
| 第一轮成功 | 不跑第二轮，耗时基本不变 |
| 第一轮失败 | 跑第二轮（转置），耗时约 ×2 |
| 前两轮都失败 | 跑 Hough（可选），再 +50% |
| 批量识别 | 进度条 + 可取消；失败的图集中列出 |

### 5.5 边界与异常

| 情况 | 处理 |
|---|---|
| 图里有多条标尺线（如 5 µm 和 50 µm 都印着，或带多个刻度的标准尺） | 交给多候选机制，最高分优先 |
| 标尺是方框（带边框） | 优先匹配"最亮的一行中位"而非 `max`；用 `_line_candidates` 的多候选挑最合理的 |
| 标尺文字在线上方 vs 下方 | 现有 `find_bar_under` 已经上下都找（`bar.py:132`），保留 |
| 图片本身是纯色/全黑 | 快速失败，返回明确文案，不跑 OCR（OCR 在纯色图上很慢） |
| 图里有多个数字（染色编号、比例数字） | 现有逻辑靠"离线条近"筛选；新增"数字与线条平行且距离 < 3 倍字高"的约束 |
| 竖标尺 + 竖排文字 | OCR 对竖排文字识别率低 → 置信度会低，走人工确认 |

### 5.6 影响文件

`core/bar.py`（主体改动：`_detect_oriented` / `TOKEN` 修复 / 打分 / 多候选 / Hough）、`ui/worker.py`（`job_calibrate` 文案与分级）、`ui/main_window.py`（多候选择选择面板 + 识别结果叠加绘制 + 橙色圆点标记）、`ui/canvas.py`（看候选线的绘制方式，可能复用现有的 `set_overlay` 机制）。

### 5.7 验收标准

1. 一张**竖标尺**的图 → 识别成功，`umpp` 与手工标定值误差 < 2%。
2. 一张横标尺的图（现有测试集）→ 识别结果与改动前**完全一致**（回归测试，不能因为改动而变差）。
3. 标尺标注 `1,000 µm` 且线长 2000 px → 算出 `umpp = 0.5`（**不是 500**）。
4. 标尺标注 `1.5 µm` → 算出正确值（小数点判定正确）。
5. 全角输入 `５０μｍ` → 归一化后识别成功。
6. 一张有多条候选线的图 → 弹出候选面板，点选后 `umpp` 正确；只有单一候选时不打扰。
7. 识别完成后在图上能看到画出的线和数字；点「不对，手动框」后线段两端已预填，微调即可。
8. 批量识别 20 张图，其中 5 张无标尺 → 5 张标记为低置信度，其余正常；总耗时相比改动前增加不超过 20%。
9. 识别出错时，`item.calib` 文案能说明卡在哪一步（找不到线 / 找到线但没读到数字 / 读到数字但没找到线 / 置信度低）。

## 附录 F 术语表

| 术语 | 含义 |
|---|---|
| 落盘 | 写入磁盘文件，程序关闭后仍然存在 |
| 工程文件（`.icproj`） | 保存完整工作区（图片清单 + 分组 + 裁剪框 + 标定 + 处理链）的 JSON 文件 |
| 处理链（`process`） | 记录在图上的有序处理步骤列表（配准 / 背景扣除 / 去卷积），可开关、可序列化 |
| 展平索引（flat index） | `(T, Z)` 二维坐标转成一维的帧号，公式 `f = t × z_count + z` |
| 烘焙 | 把显示区间等显示设置直接写入像素值。原始位深导出必须避免烘焙 |
| 取样线 | 正交视图用的一条线，沿它切出 XZ 或 YZ 剖面 |
| 候选 | 标尺识别给出的多个可能的标尺位置/数值，供用户选择 |
| **链前数据** | 处理链**应用之前**的像素值。原始位深导出时内嵌进 TIFF，用来做"精确还原" |
| **链后数据** | 处理链**应用之后**的像素值。原始位深导出的主页面内容 |
| **私有 tag** | TIFF 规范允许的自定义标签（本方案用 65000/65001…）。其它软件会忽略，不影响读图 |
| **精确还原** | 重新导入导出件后，能逐像素回到链前状态（`np.array_equal` 为真），不依赖逆运算 |
| **指纹**（拼接复用） | 文件大小 + 修改时间 + 图像尺寸；三项一致就复用磁盘上拼好的图，不重拼 |
| **清晰度冻结** | §2.7 的硬约束：默认状态下预览观感与 v1.1 一致（拉普拉斯方差偏差 < 5%） |

### H.20 MagnifyingDock 移植（Bencho · MIT）（2026-11-02）

原组件是 React + CSS 变量；本项目是 PySide6，没有 npm/React/CSS，因此按**行为**移植成
Qt 控件，落在 `app/ui/magnifying_dock.py`：

| 原行为 | Qt 实现 |
|---|---|
| 距离衰减放大（raised cosine，spread 控制波及范围） | `_falloff(d) = (1+cos(πd/(spread+1)))/2`，`d>spread` 归零 |
| 事件挂在整条 bar 上，索引 = 离指针最近的 item 中心 | `mouseMoveEvent` → `_at(x)` 量每个 item 中心 |
| 只放大 glyph，不放大按钮/圆点/标签 | 绘制时只对 20px 图标做 scale + translateY |
| 一个会移动的 tooltip，宽度过渡到新词 | 每帧按当前项算宽、画深色药丸（160ms 缓动由 pos 动画驱动） |
| 活动项下方 3px 圆点 | 画在 item 内底部 |
| 透明度 0.42 / 0.66 / 1.0 三档 | 按 d 连续插值，避免跳变 |

**令牌映射**（原 CSS 读的 var() 在本项目没有对应机制，逐个对到已有值；没有对应物的
玻璃组就地定义，不泄漏成全局）：

`--pane`→CARD+透明、`--pane-edge`→theme.LINE、`--ink`→theme.TEXT、
`--ink-rgb`→"33,30,24"、`--on-ink`→#FFFFFF、`--fill-on`→theme.TEXT、`--fill-slab`→#FFFFFF、
`--font-ui`→theme.FONT、`--shadow-rgb`→"33,30,24"、`--try-edge`→theme.LINE；
`--g-*`（玻璃）→ 组件内 `TOKENS`，Qt 无 backdrop-filter，用半透明面+顶部高光+柔影近似。

放置：浮在画布 stage 底部中间（不占布局），事件里重定位；点击发 `activated(key)`，

### H.34 修「双击没反应」：自动保存提示框不可见（2026-11-02）

**现象**：被强杀（或没走正常关闭）之后再次启动，进程活着、CPU 几乎为 0，但窗口一直不出现。

**定位**：用 `faulthandler` 抓栈，卡在 `_check_autosave()` 的

1. `_check_autosave()` 先确认 `self.isVisible()` 且 `windowHandle() is not None`，
   不满足就 400ms 后重试，避免在窗口还没映射时弹模态框；
2. 提示框改成显式构造 + `show()`（非阻塞），用 `finished` 信号处理结果，
   不再用阻塞的 `QMessageBox.question`。

验证：人为把 `config/last_exit.txt` 改旧（制造「异常退出」条件）后再启动，
`上次没正常退出` 对话框与主窗口**都能正常出现**。

### 更正：H.34 的「启动卡死」其实是我的测试脚本造成的

后续排查发现：我批量测试时会在同一个 PowerShell 会话里先设

予以保留，但它**不是**该现象的成因。以后启动程序前必须确保 `QT_QPA_PLATFORM` 未设置。

### H.49 时间轴拖动卡顿：节流 + 播放按钮（2026-11-03）

**卡顿的原因（实测，不是猜的）**：

```
20 次鼠标移动           1072 ms   → 53.6 ms / 次
on_frame_changed 单次     49.6 ms
WakeSlider.paintEvent     0.35 ms   ← 画条子不是瓶颈
```

瓶颈是 `valueChanged` → `on_frame_changed`（解码 + 合成那一帧预览，约 50ms），而拖动时
**每移动一次就发一次**，UI 线程被这 50ms 按住，所以手感是“一格一格卡”。

**修法**：拖动期间把 `valueChanged` 节流到最多 90ms 一次（约 11 次/秒），松手时立刻补发
最后一帧。条子的视觉更新仍是每帧刷新，所以拖尾动画不受影响。

结果：**20 次移动 1072ms → 17.9ms（53.6 → 0.9 ms/次）**，拖动跟手，图像以约 11fps 追赶。

### H.50 拖尾动画不再卡：拖动时只更新读数不换帧；播放图标与倍率（2026-11-03）

**拖尾动画为什么还卡**：H.49 把换帧节流到 180ms，但每次换帧要 **50ms**，那 50ms 里
UI 线程被占住，60fps 的拖尾定时器就被饿死 —— 表现就是“条子一顿一顿”。

**这一版的做法**：拖动期间**完全不换帧**。

- `WakeSlider` 拆出两个信号：
  - `valuePreview(int)` —— 每次取整变化都发，只用来改「第 x/y 点」这行字（几乎零成本）
  - `valueChanged(int)` —— 节流到 500ms，且**松手时立刻补发**，用来真正换帧
- 实测：20 步拖动期间 **换帧 0 次、读数更新 21 次**，松手后 **1 次**换帧。
  拖尾动画因此全程 60fps，不再被 50ms 的渲染打断。

**播放按钮**：换成 Lucide `circle-play`（用户提供）；播放中显示「圆环 + 两竖线」的暂停态。

**播放速度**：基准 1× = **4 秒放 50 张（80ms/帧，12.5 帧/秒）**，
旁边一个下拉框可选 **1/4× · 1/2× · 1× · 2× · 3×**（320 / 160 / 80 / 40 / 27ms），
播放中切换会立即按新倍率重排定时器。

回归：`smoke` 通过。

### H.51 播放自适应调速 + 拖动时的图像更新节奏（2026-11-03）

实测（1024² 的图，热缓存）：

| 动作 | 耗时 |
|---|---|
| `refresh_preview()` | 3.6 ms |
| `refresh_manifest()` | 0.05 ms |
| `_sync_frame_ui()` | 0.02 ms |
| `on_frame_changed()` 整帧（含解码/合成） | **13–48 ms** |

换一帧的真实成本在 13–48ms 之间（取决于该帧是否已在缓存里），这就是“图像跟不上手”的根源。

**播放调速**：改成**自适应 + 丢帧**——
每帧记下渲染耗时，定时器间隔取 `max(目标间隔, 渲染耗时 × 1.15)`。
宁可少放几帧，也不让事件队列堆积（堆积的表现就是整块界面卡住）。

实测：1× 稳定 **12.5 帧/秒**（80ms，正好 4 秒 50 张）；3× 目标 27ms，
实际 56ms 一帧（**17 帧/秒**）—— 受限于单帧渲染成本，已到机器上限。

**拖动时**：换帧节流 200ms（约 5 次/秒），松手立刻补最后一帧。
拖动期间实测：24 步里换帧 **1 次**、松手再 **1 次**，拖尾动画全程 60fps。

### 关于两处“卡顿”的取舍（留给用户决定）

拖动时，**条子顺滑**和**图像顺滑**互相冲突：换一帧要 48ms，这段时间 UI 线程被占住，
60fps 的拖尾就会顿一下。

- 现在的选择：**条子优先**（200ms 才换一次帧，条子基本不顿，图像约 5 帧/秒跳）
- 若更想让图像跟手：把 `wake_slider.py` 的 `_emit_timer.start(200)` 改成 `60`，
  图像约 10 帧/秒、更连续，但条子会跟着一顿一顿
- 根治办法是把 `refresh_preview` 挪到后台线程（渲染在 worker、贴图回主线程），
  这样两边都顺 —— 但那是预览链路的改造，需要单独一轮并跑完整自检

### H.52 根治：预览渲染移到后台线程（2026-11-03）

**最后一层瓶颈在哪**（实测单帧 1024²）：

| 环节 | 耗时 |
|---|---|
| `preview_for_view`（解码 + 重采样） | **19.2 ms** |
| `compose`（合成通道） | 1.0 ms |
| `sharpen_display`（屏幕锐化） | **20.9 ms** |
| `canvas.set_image` | 2.6 ms |

合计 ~44ms，全在 UI 线程上跑 —— 所以「条子顺」和「图像顺」只能二选一。

**做法**：这两块纯 numpy 的重活已经全部放到后台线程（`QThreadPool` + `QRunnable`）。

- 只在**正在播放**或**正在拖时间轴**时走异步（`self._fast`）；其它时候仍是同步渲染，
  所以 `smoke` / `roi_check` / `view_switch_check` / `export_check` 的行为一行没变。
- 单线程池、同一时刻只跑一个任务，新的请求覆盖旧的（`_prev_gen` 序号丢弃过期结果）。
- 结果回主线程只做 `canvas.set_field / set_pix_um / set_image` 这几下（2.6ms）。

### H.59 灰带根除（任意文件类型都不会再出现）+ 性能体检（2026-11-03）

**灰带的真正来源**：`QFrame#chipCard` 里面不止一层容器 —— `chips`（三个信息格）、
`frames_row`、以及它里面的 `z_row` / `t_row`，每层都是普通 `QWidget`。
全局 QSS 的 `QWidget { background: BG }` 会给**每一层**刷页面底色，

这一版改成**按范围兜底**，不再逐个点名：

```
QFrame#chipCard, QFrame#chipCard QWidget { background: transparent; }
QFrame#chipCard QComboBox, QFrame#chipCard QLineEdit,
QFrame#chipCard QSpinBox, QFrame#chipCard QDoubleSpinBox { background: field; ... }
```

第一条把这条带子里**所有**普通容器清成透明；第二条把真正的输入控件（播放倍率那种）
重新给回输入框底色。以后这条带子里再加什么行（Z 行、声明按钮、时间轴…）都不会再出灰带。

### H.63 修复卡顿：投影改成缓存位图 + 开关空闲停表（2026-11-03）

用户反馈：裁剪框缩放/拖动变卡，导出窗口的开关也卡。

**原因一（主因）：`QGraphicsDropShadowEffect`**。
挂在 `#workspace` 上的这个 effect 会让**每一次画布重绘**都走一遍离屏渲染 + 16px 模糊。
实测同一段画布重绘：

| 状态 | 每帧耗时 |
|---|---|
| 带 `QGraphicsDropShadowEffect` | **20.2 ms** |
| 去掉 effect | 1.3 ms |
| 改成缓存投影位图（现在） | **2.1 ms** |

所以裁剪框一拖，整块白板每帧重新模糊一次 —— 拖动和缩放直接掉到 ~50ms/帧。
**修法**：新增 `BodyWidget` 作为主区域容器，在 `paintEvent` 里把预先算好的一张
投影位图（圆角矩形一圈圈叠加，尺寸变化才重算，一次约 1ms）画在白板底下。
画布怎么刷都不会再触发模糊，投影观感保留。

**原因二：液体开关的定时器从不休眠**。`LiquidSwitch` 之前一建好就跑 16ms 定时器，
导出窗里 9 个开关 = 每秒 560 次回调 + 重绘。
**修法**：加 `_wake()`，有交互（按下/移动/进出/切换）才启动；状态彻底静止后自己 `stop()`。
实测切换一个开关期间事件循环仍有 **30 万次/秒**，静止后定时器确认已停。

验证：裁剪框拖动改为逐帧重绘 **2.1ms**（原来 20.2ms），拖动/缩放跟手；导出窗 9 个开关
切换瞬时响应，空闲不占 CPU。

回归：`smoke` / `roi_check` / `view_switch_check` 全通过。

### H.65 标尺文字距可调 · 开关误触修复 · 切图不再卡（2026-11-03）

**1. 标尺文字离标尺的距离不可调**

但**界面上没有入口**。现在标尺卡片新增「文字距 (px)」输入框（留空 = 自动），

`LiquidSwitch` 的拖动逻辑里，只要 `mouseMoveEvent` 触发就按「拇指越过中线」翻转状态。
问题：**刚点完、弹簧还在跑**的时候（拇指在中线附近），一次 1px 的鼠标移动就会把状态
再翻回去，松手时又翻一次 —— 肉眼就是「自己快速开关一下」。

修法：切图时把这一轮预览交给已有的后台渲染通道（`_switching` 标志），点下去立刻返回，
约 50ms 后画面自动补上。

（自检脚本与 `offscreen` 平台强制同步，保证用例语义不变。）

### H.70 删除最后一张图后画面卡住（2026-11-03）

**现象**：导入一张 PNG → 删除 → 主界面还留着那张图，右栏/标题也不更新。

**根因**：为了切图不卡，预览改成了后台线程渲染（H.65）。删除图片时 `cur_item` 被置空、
`refresh_preview()` 立刻把画布刷成黑底，但**之前那张图的后台渲染还在路上**；
它回来时 `gen == _prev_gen`（删除时没有让在途任务作废），于是把已经删掉的图像又画回画布，
而且之后没有任何刷新，就永久卡在那里。

**修法（两层）**：

1. `_on_preview_done()` 增加身份校验：`spec["item"] is not self.cur_item` 或
   `cur_item is None` 时**直接丢弃结果**，不碰画布。这样切图、删除、换组都不会串帧。
2. 新增 `_clear_view()`：作废在途预览（`_prev_gen += 1`、清 `_prev_pending / _planes_key /
   _base_key / _used_rect`）、清空 `cur_item / cur_group`、标题改「还没有导入图片」、
   清空 px / size 标签、关掉裁剪框与叠加层、画布置空，并统一刷新通道卡、ROI、清单、Z/T 行。

**同类路径一并收口**（都改成走 `_clear_view()`）：

| 入口 | 之前 | 现在 |
|---|---|---|
| `remove_item()` 删掉最后一张 | 只 `refresh_preview + refresh_channels` | `_clear_view()` |
| `clear_all()` 清空列表 | `refresh_preview()`（同样会被在途任务画回来） | `_clear_view()` |
| `proj_new()` 新建工程 | 残留上一张图 | `_clear_view()` |

验证：导入 → 删除 → `cur_item=None`、标题「还没有导入图片」、px 为空、画布黑；
清空列表、新建工程同样干净；再导入一次能正常工作。
回归：`smoke` / `roi_check` / `view_switch_check` 通过。

### H.71 原图视图播放不滚动 + 重新封装 1.0.1（2026-11-03）

**现象**：时间轴序列在「原图」视图下播放，画面停在某一帧不再刷新（切到「裁剪」视图正常）。

**为什么只有原图视图**：原图视图走的是后台渲染通道（H.65，为了切图不卡）；
裁剪视图是同步渲染。所以一旦后台那条管线堵住，原图视图的画面就再也不更新，
而其它一切（滑条、帧号、状态栏）都还在正常跑 —— 看起来就是「不滚动」。

**修法（三道保险）**：

1. **卡死自愈**：`_start_preview_job()` 记录 `_prev_t0`；`_preview_async()` 发现
   `_prev_busy` 已经超过 **0.8s** 还没回来，就判定这次后台渲染丢了，丢掉它重开一单
   —— 队列不会永久堵住。
2. **播放前清场**：`on_play_toggled(True)` 调 `_play_reset_async()`，把上一轮挂起的
   `_prev_busy / _prev_pending` 清掉。
3. **落后就同步**：`_play_step()` 比较「画面真正显示的帧 `_drawn_frame`」和「当前帧」，
   连续 **3 拍**都还没跟上，就把这一拍改成同步渲染（宁可慢一帧也不能停住）。

实测（人为把 `_prev_busy` 置 True 模拟卡死）：播放仍然滚动，帧序列
`1,2,3,3,4,5,6,6,7,0,1,1`，8 帧全覆盖；正常情况帧序列 `1..5,0` 循环，6 帧全覆盖。

### H.72 播放卡顿·倍率弹框卡顿·漂移矫正重做（2026-11-03，1.0.2）

**1. 播放卡顿**
两个原因：

- H.71 里「连续 3 拍落后就同步渲染」实际上是在播放回调里**同步**跑 40–150ms 的渲染，
  这本身就是卡顿源 —— 整段删除，改成「落后只丢帧」；
- 播放时仍在按画布原分辨率渲染（2048² 源下每帧 ~80ms），3× 只跑到 12.7 帧/秒。

修法：播放/拖动时按**倍率自适应降分辨率**渲染，停下后自动补一张清晰版：

| 倍率 | 渲染比例 | 实测 |
|---|---|---|
| ≤1× | 0.70 | **12.0 帧/秒**（目标 12.5） |
| 2× | 0.50 | **24.7 帧/秒**（目标 25） |
| 3× | 0.38 | **33.3 帧/秒**（目标 37.5） |

同时把后台「卡死判定」阈值从 0.8s 放宽到 2.5s（0.8s 对大图会把还在跑的活杀掉）。

**2. 调倍率时弹框卡顿**
播放中每 27–80ms 就有一帧渲染排队，下拉弹出时和它抢 UI 线程。
修法：监听倍率下拉 `view()` 的 Show/Hide，**弹出期间冻结推帧**，选完自动继续。
实测：弹框打开 0.6s 内推帧 **0 次**，关闭后立刻恢复 7 帧/0.6s。

**3. 时间序列漂移矫正「矫正得不行」**
原实现是**每帧直接和参考帧做相位相关**。漂移是累积的，远处帧位移大，
全分辨率相位相关要么算飞、要么响应极低 —— 估出来的位移基本是噪声。

重写 `core/register.py · drift_shifts()`：

1. **相邻帧累加**：先估相邻帧的小位移（可靠），再沿时间轴累加成相对参考帧的绝对位移；
2. **双路校验**：每帧再和参考帧直接相关一次，响应 ≥0.08 且与累加值不矛盾就用直接值
   （无累积误差），0.02–0.08 之间取两者中值，否则用累加值；
3. **大位移兜底**：直接相关若位移超过画幅 35%，在 1/4 缩小的图上重算再放大；
4. 多通道帧取**最大强度**合成后再配准（信噪比比单通道高）。

验证（合成序列，每帧真实漂移 dx=+7 / dy=+4，第 7 帧累计 49/28 px）：

| 帧 | 真实 | 估计 |
|---|---|---|
| 1 | (7.0, 4.0) | (7.0, 4.0) |
| 3 | (21.0, 12.0) | (21.0, 12.0) |
| 5 | (35.0, 20.0) | (35.0, 20.0) |
| 7 | (49.0, 28.0) | (49.0, 28.0) |

**最大误差 0.06 px**。方向也验证过：`est_shift` → `apply_shift` 后相关系数
由 -0.019 提升到 0.966。

`ImageCapture_1.0.2_portable_win64.zip`（95.6 MB）已替换 1.0.1 产物，

### H.73 贴边分屏 / 边缘缩放（1.0.3，2026-11-03）

**两个现象**：① 拖标题栏到屏幕边缘不触发分屏或最大化；② 换台电脑装完之后，
拖边框完全改不了大小。

**根因是同一个**：这是无边框窗口（`FramelessWindowHint`），Qt 建出来的窗口**没有
`WS_THICKFRAME`**。Windows 的 Aero Snap（贴边分屏）只对「可缩放窗口」生效，所以拖到边缘
没有反应；而缩放只能靠自绘的 6px 热区（`ResizeEdge`）在 Python 里算几何 ——
换机器/换 DPI/换缩放比例后热区位置和鼠标命中对不上，就完全失效。

**修法：把窗口重新变成「系统眼里的可缩放窗口」，但外观不变。**

1. 窗口显示之后（`QTimer.singleShot(0)`，不能在创建前改，否则 `CreateWindowEx` 直接失败）
   给 HWND 补上 `WS_THICKFRAME | WS_MAXIMIZEBOX | WS_MINIMIZEBOX | WS_SYSMENU`，
   `SetWindowPos(..., SWP_FRAMECHANGED)` 让样式生效；
2. `WM_NCCALCSIZE` 返回 0 → 客户区仍然铺满整窗，**看不到系统边框**，圆角白板照旧；
   但「最大化」时按 `SM_CXSIZEFRAME + SM_CXPADDEDBORDER` 内缩，不会盖住任务栏、不会被切边；
3. `WM_NCHITTEST` 自己接管：先判 6 逻辑像素的边缘 → 返回 `HTLEFT/HTTOP/...`（交给系统拖动缩放），
   再判标题栏 → `HTCAPTION`（由系统执行真正的移动，于是**贴边分屏、双击最大化全都回来了**）；
4. 自绘的 `ResizeEdge` 热区在原生模式生效后全部隐藏并设成 `WA_TransparentForMouseEvents`，
   `_place_edges()` 里也跳过它们；原生方式失败时（非 Windows / 权限问题）自动退回自绘热区。

**踩到的坑（记一笔）**：一开始把「补样式」放在 `showEvent` 里同步执行，启动瞬间
`CreateWindowEx failed` + `0xc000041d`（Qt6Core 里的用户回调异常）直接崩；
改成 `singleShot(0)` 延迟执行，并让 `nativeEvent` 在 `_native_frame` 生效之前**完全不接管**
`WM_NCCALCSIZE`，才稳定。实测：开发版与安装版都能正常启动，标题 `1.0.3`，
`WS_THICKFRAME=True`、最大化后窗口等于工作区。

**封装**：`ImageCapture_Setup_1.0.3.exe`（66.0 MB）/ `ImageCapture_1.0.3_portable_win64.zip`（95.6 MB），
静默安装 → 启动 → 卸载干净已实测；1.0.2 产物已删除。

### H.74 安装包打不开 .oib 的根因：imagecodecs 的 68 个编解码器没打进去（1.0.4，2026-11-04）

**现象**：别人电脑装好之后打不开原始文件（.oib / .czi / .lif），作者本机正常。

**为什么本机正常**：本机跑的是开发版，用的是 `runtime\python` 里**完整安装**的
site-packages；打包版是另一套环境。

**根因**：`imagecodecs` 2026 版把每种编解码器拆成了独立的扩展模块

```python
_IC_BINARIES = [(f, "imagecodecs") for f in glob.glob(os.path.join(_IC_DIR, "*.pyd"))]

binaries=_IC_BINARIES
hiddenimports += ["tifffile", "czifile", "oiffile", "liffile", "imagecodecs"]
```
